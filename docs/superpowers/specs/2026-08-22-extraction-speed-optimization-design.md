# SmartZip 解压速度优化设计

**日期：** 2026-08-22
**范围：** 在保持现有解压结果、安全门和用户交互不变的前提下，减少同一次解压流程中的重复 7-Zip 子进程。

## 目标

降低加密压缩包和嵌套压缩包的解压延迟，重点减少已经完成的探测/完整性验证被重复执行的情况。

优化只改变内部结果传递，不改变 SmartZip 对用户可见的功能、设置语义、诊断分类或源包处理规则。

## 当前瓶颈

当前 `SmartZip.ahk` 的单包流程包含以下逻辑阶段：

1. `ProbeArchive` 用 `7z l -slt` 探测格式、加密和分卷信息。
2. 对需要密码的包，`ResolveArchivePassword` 会用 `7z t` 验证空密码和密码候选。
3. 当 `test`、源包回收或嵌套源包处理需要完整性检查时，外层流程再次调用 `TestArchive`。
4. `ExtractArchiveToTemp` 解压到隔离临时目录，并在解压后执行一次 `7z t` 以获得最终完整性和警告信息。
5. 嵌套包在 `UnZipNesting` 中已经完成一次 `ProbeArchive`，随后进入 `Unzip` 又会对同一路径重新探测。

其中第 3 步在密码验证成功的路径上属于重复的完整性验证进程；第 5 步属于重复的探测进程。第 4 步不能在本设计中移除，因为它仍承担解压结果的最终诊断职责。

## 不变约束

- 保留 `probe -> optional test -> isolated extract -> finalize` 的安全流水线语义。
- 不减少任何逻辑上必需的完整性检查；只复用同一次调用链中已经成功得到的验证结果。
- 保持 `OK`、`OK_WITH_WARNING`、密码错误、数据损坏、缺卷、取消和其他诊断分类不变。
- 保持密码候选顺序、交互式重试、批量不弹密码框和密码保存行为不变。
- 保持隔离临时目录、部分输出隔离、源包回收站处理和嵌套源包回收门槛不变。
- 保持 `7zG.exe` 的现有 GUI 路径、进度显示、隐藏规则、命令行参数和配置项不变。
- 不引入跨运行缓存、不并行解压、不修改 7-Zip 压缩级别或线程参数。
- 内部优化字段不得进入诊断日志、脱敏复制内容、集成结果 JSON 或其他用户可见输出。

## 方案比较

### 方案 A：传递已验证的 `TestArchive` 结果（推荐）

让成功的 `TestArchive` 结果带一个内部 `testVerified` 标记。密码预检成功后，外层 `zipx` 在需要执行逻辑测试阶段时直接使用这个结果；如果标记不存在、路径不匹配或结果不是成功状态，仍走原来的 `TestArchive` 调用。

优点：

- 加密包可少启动一个重复的 `7z t` 进程。
- 不跳过完整性验证，验证仍由同一个 `7z t` 结果提供。
- 失败、警告和密码恢复路径可以保留原有分支。
- 只需要内部结果字段和一个明确的回退条件。

代价：

- `zipx` 需要区分“探测成功”和“已经完成测试”。
- 测试宿主需要增加结果传递契约。

### 方案 B：嵌套流程传递已完成的探测结果（推荐）

让 `UnZipNesting` 把刚刚完成的 `ProbeArchive` 结果传给 `Unzip`，再由 `zipx` 在路径匹配时直接使用；顶层调用和不匹配场景仍调用原有 `ProbeArchive`。

优点：

- 每个嵌套候选可少启动一个重复的 `7z l` 进程。
- 不使用跨运行缓存，避免外部文件变化后读到旧结果。
- 保留 `ProbeArchive` 的原始调用作为安全回退。

代价：

- `Unzip` 和本地 `zipx` 闭包增加一个可选的预检结果参数。
- 嵌套测试需要验证结果确实沿调用链传递。

### 方案 C：改用纯命令行解压或并行解压

让所有解压都走 `7z.exe`，或对批量任务并发启动多个 7-Zip 进程。

这类方案可能带来更明显的吞吐变化，但会改变进度窗口、进程管理、磁盘竞争、批量顺序或故障隔离行为，和“现有情况不变”的约束冲突。本轮不采用。

## 采用的设计

本轮采用方案 A + B，且只在同一次同步调用链内传递结果。

### 1. 已验证测试结果传递

`TestArchive(path, password)` 在状态为 `OK` 或 `OK_WITH_WARNING` 时继续设置现有的 `passwordUsed`，并额外设置内部布尔字段 `testVerified := true`。失败结果不设置该字段。

`zipx` 计算现有的 `forceTest` 条件后：

- 若 `resolved` 是来自成功 `TestArchive` 的结果，且其 `archivePath` 与当前归一化后的 `path` 相同，则把 `resolved` 作为 `tr` 使用；
- 否则执行原有的 `this.TestArchive(path, resolved.passwordUsed)`；
- 后续对 `tr.status`、警告、数据损坏、密码重试和源包处理的判断保持原样。

不把密码复制到新的性能字段中。现有 `passwordUsed` 仍只在内存结果对象中使用，生产诊断和测试结果导出继续按当前规则排除它；`testVerified` 也不加入任何输出组合。

### 2. 嵌套探测结果传递

`UnZipNesting` 完成候选判断和 `ProbeArchive(path)` 后，对接受进入嵌套解压的路径调用 `this.Unzip(path, probe)`。

`Unzip` 增加可选的 `preProbe` 参数，并将其传给本次唯一的 `zipx` 调用。`zipx` 在分卷归一化后仅当 `preProbe.archivePath` 与当前 `path` 大小写不敏感地匹配时使用预检结果；否则执行原有 `ProbeArchive(path)`。

这样，正常顶层调用的行为完全不变；嵌套调用只复用刚刚得到且尚未有机会被修改的同一路径结果；路径不匹配时自动回退，不会扩大缓存有效范围。

### 3. 保留最终解压后测试

`ExtractArchiveToTemp` 中的解压后 `7z t` 保持不变。它负责将实际解压过程的退出码和警告文本与最终输出状态结合，不能由密码预检结果或嵌套探测结果替代。

## 测试设计

实现采用 TDD，每个优化先添加失败断言，再添加最小生产改动。

### 密码验证结果

- 在密码预检测试中增加成功 `TestArchive` 结果含 `testVerified` 的断言。
- 增加 `OK_WITH_WARNING` 也可复用、失败状态不可复用的断言。
- 增加 `zipx` 的静态契约断言：保留 `forceTest`，优先使用已验证结果，同时保留 `TestArchive` 回退调用。
- 确认新字段不会出现在诊断字段组合和集成结果 JSON 中。

### 嵌套探测结果

- 在嵌套迁移测试中增加 `Unzip` 接收预检结果的调用记录。
- 验证顺序仍为候选判断 -> `ProbeArchive` -> 嵌套 `Unzip`。
- 验证非归档探测结果不会进入嵌套解压。
- 验证路径不匹配时 `zipx` 回退到 `ProbeArchive`。

### 回归与性能证据

- 运行密码、嵌套、解压生命周期和静态契约测试。
- 运行完整 8 套契约门禁，所有原有场景继续通过。
- 使用相同的真实 7-Zip fixtures 对比优化前后的子进程调用次数：加密验证路径少一次 `7z t`，嵌套路径少一次 `7z l`，普通单包不应新增调用。
- 记录代表性场景的总耗时作为性能证据，但不设置易受机器负载影响的硬编码时间阈值。
- 最后运行 `git diff --check`。

## 验收标准

1. 现有功能和安全处理的契约测试全部通过，新增结果传递断言通过。
2. 加密包的成功密码验证路径不再重复执行同一 `TestArchive`，但解压后最终测试仍执行。
3. 嵌套包不再对同一路径重复执行紧邻的 `ProbeArchive`，路径不匹配时安全回退。
4. 普通顶层包、失败包、警告包、分卷、取消和批量处理的行为保持原样。
5. 生产源码没有测试钩子、明文密码泄露或跨运行缓存。
6. `git diff --check` 通过，测试文档中的精确计数与实际结果一致。
